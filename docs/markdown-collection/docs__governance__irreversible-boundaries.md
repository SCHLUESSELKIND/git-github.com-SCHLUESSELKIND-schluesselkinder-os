# Irreversible Boundaries

## Purpose

Some capability classes create irreversible external effects or hard-to-reverse governance damage.

These boundaries must be protected before any future escalation.

## Irreversible External Effects

High-risk effects:

- public channel action
- account mutation
- payment creation
- fulfillment creation
- provider-side file transfer
- timed external workflow
- background process moving material across states

None exist in the current system.

## Irreversible Governance Damage

High-risk governance failures:

- evaluation treated as approval
- score treated as truth
- export treated as permission
- review snapshot treated as approval
- review status mutated without append-only decision history
- AI system creating final approval records
- platform metrics overruling brand constraints

## Pre-Execution Requirements

Before any irreversible class is introduced:

- auth and actor identity must exist
- append-only authority trail must exist
- review transition policy must exist
- route-surface regression must be expanded
- dependency audit must be expanded
- terminology review must pass
- authority-leak audit must pass
- rollback or kill path must be documented

## Permanent Boundaries

These remain disallowed:

- autonomous public channel action
- score-based approval
- AI approval decisions
- unofficial social automation
- engagement-first optimization
- commerce contamination of the object archive
- creator-platform reframing

## Current Safe State

The current system is safe because it remains:

- read-only at API surface
- review-bound
- non-autonomous
- non-delivering
- non-provider-enabled
- non-worker-enabled
- non-commerce-enabled

## Conclusion

Capability should increase only after the system can prove it will not convert inspection into authority.
